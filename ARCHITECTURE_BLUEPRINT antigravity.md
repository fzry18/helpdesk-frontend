## 1. ANALISIS KONDISI SAAT INI (AS-IS)

### Masalah Arsitektur yang Ditemukan

| # | Masalah | Dampak |
|---|---------|--------|
| 1 | `src/store/authStore.ts` berada di root, tapi store ticket ada di `src/features/tickets/stores/` — inkonsisten | Membingungkan developer baru |
| 2 | `src/pages/` dan `src/app/` coexist — Next.js hanya mendukung satu router aktif | Potensi konflik routing |
| 3 | `src/types/index.ts` menjadi satu file monolitik 6KB+ | Sulit untuk di-tree-shake, sulit di-maintain |
| 4 | `src/lib/` berisi campuran: api client, query config, socket, server utilities — tanpa hierarki jelas | Coupling tinggi, sulit tes unit |
| 5 | API proxy routes (`src/app/api/helpdesk/[...path]`) digunakan sebagai pass-through ke Odoo tanpa abstraction layer | Sulit tambah caching, rate limiting, transformation |
| 6 | Socket.IO manager (`ws-manager.ts`) terisolasi di dalam `features/realtime/` tanpa kontrak interface | Sulit di-mock untuk testing |
| 7 | `src/components/` tidak terstruktur FSD — bercampur antara: ui primitives, domain components, layout | Tidak scalable |

## 2. ARSITEKTUR TARGET (TO-BE)

### Filosofi Desain

Proyek ini mengadopsi **Feature-Sliced Design (FSD)** yang dikombinasikan dengan **Next.js App Router conventions**. Prinsip utama:

1. **Separation of Concerns**: Business logic ≠ UI ≠ State ≠ Transport
2. **Dependency Direction**: `app` > `features` > `entities` > `shared` — tidak boleh dibalik
3. **Server-first**: Semua komponen adalah Server Components secara default; `'use client'` hanya ketika mutlak diperlukan
4. **Colocation**: Setiap fitur memiliki komponen, hooks, types, dan stores sendiri
5. **Single Source of Truth**: Satu store per domain, satu type-file per entity

## 4. DESIGN PATTERNS YANG DIREKOMENDASIKAN

### 4.1 Layer Architecture (Dependency Direction)

```
┌─────────────────────────────────────┐
│           app/ (Pages)              │  Next.js routes, layouts, RSC
├─────────────────────────────────────┤
│         features/ (Feature Slices)  │  Domain logic, koherensi bisnis
├─────────────────────────────────────┤
│         entities/ (Shared Models)   │  Cross-feature type definitions
├─────────────────────────────────────┤
│         shared/ (Infrastructure)    │  UI primitives, lib, utils
└─────────────────────────────────────┘
        ↑ Impornya SEARAH ke bawah saja
```

### 4.2 Server vs Client Component Split

```
app/(dashboard)/tickets/page.tsx      ← Server Component (data fetching via Prisma/API)
└── features/tickets/components/
    ├── TicketFilters.tsx             ← 'use client' (interaktif, filter state)
    ├── TicketList.tsx                ← 'use client' (useQuery, realtime)
    └── TicketFormDialog.tsx          ← 'use client' (form, mutations)
```

**Aturan:**
- `app/*/page.tsx`: **Server Component** — fetch data awal, pass sebagai initial props/dehydrated state
- Komponen yang butuh `useState`, `useEffect`, event handler: wajib `'use client'`
- **Jangan pernah** import server libraries (`prisma`, `jsonwebtoken`) di Client Components

### 4.3 Repository Pattern untuk API Routes

Setiap API route handler **tidak boleh** berisi business logic. Gunakan service layer:

```typescript
// ❌ JANGAN — logic di route handler
// app/api/helpdesk/tickets/route.ts
export async function GET(req: Request) {
  const tickets = await prisma.ticket.findMany({ where: { status: 'open' }, ... })
  // sorting, filtering logic langsung di sini
}

// ✅ SEBAIKNYA — gunakan service
// shared/lib/server/ticket.server.ts
export async function getTickets(filters: TicketFilters): Promise<PaginatedResponse<Ticket>> {
  // semua logic di sini, testable
}

// app/api/helpdesk/tickets/route.ts
import { getTickets } from '@/shared/lib/server/ticket.server'
export async function GET(req: Request) {
  const filters = parseFilters(req)
  const data = await getTickets(filters)
  return Response.json(data)
}
```

### 4.4 Query Key Factory Pattern (Sudah Digunakan — Pertahankan)

```typescript
// shared/lib/query/config.ts
export const queryKeys = {
  tickets: {
    all: ['tickets'] as const,
    lists: () => [...queryKeys.tickets.all, 'list'] as const,
    list: (filters: TicketFilters) => [...queryKeys.tickets.lists(), filters] as const,
    details: () => [...queryKeys.tickets.all, 'detail'] as const,
    detail: (id: number) => [...queryKeys.tickets.details(), id] as const,
  },
  // ... fitur lain
}
```

### 4.5 Store Architecture (Zustand)

**Satu store per domain**, bukan satu store global:

```typescript
// features/auth/stores/auth.store.ts       — Auth state
// features/tickets/stores/ticket-filter.store.ts  — UI filter state
// (buat jika diperlukan) features/tickets/stores/ticket-selection.store.ts — Multi-select state
```

**Wajib menggunakan selector untuk mencegah excessive re-render:**
```typescript
// ✅ Spesifik selector
const isAdmin = useAuthStore(selectIsAdmin)

// ❌ Subscribe seluruh store
const { employee, isAdmin, logout, ... } = useAuthStore()
```

### 4.6 Zod Schema Colocation

Schema validasi harus berada di dalam fitur terkait:

```typescript
// features/tickets/schemas/ticket.schema.ts
export const createTicketSchema = z.object({
  title: z.string().min(5, 'Minimal 5 karakter'),
  description: z.string().min(20),
  priority: z.enum(['low', 'medium', 'high', 'urgent']),
  category_id: z.number().positive(),
})

export type CreateTicketInput = z.infer<typeof createTicketSchema>
```

### 4.7 Real-time Architecture (Socket.IO)

Socket harus dikelola sebagai **singleton** dengan Provider pattern:

```
RealtimeProvider (Context)
└── socket-manager.ts (Singleton, koneksi + event bus)
    └── Domain hooks: use-ticket-realtime.ts menggunakan socket.on(...)
        └── Invalidate TanStack Query cache pada event tertentu
```

### STEP 5 — Refactor API Route Handlers dengan Service Layer

**Estimasi:** 2-3 jam  
**Risiko:** Tinggi (core functionality)

**Konteks:** API routes di `src/app/api/helpdesk/` saat ini mungkin berisi business logic langsung. Kita perlu memisahkan ke server-side services.

**Tindakan:**
1. Buat `src/shared/lib/server/` dengan files:
   - `db.ts` — Prisma client singleton
   - `auth.ts` — JWT verification, `getServerSession(req)` helper
   - `odoo.ts` — Odoo REST client dengan base URL dari env
2. Untuk setiap resource yang penting (tickets, dashboard), buat server service:
   ```typescript
   // src/shared/lib/server/services/ticket.server.ts
   export async function getTicketList(filters: TicketFilters, userId: number) { ... }
   export async function createTicket(input: CreateTicketInput, userId: number) { ... }
   ```
3. Refactor route handlers untuk hanya handle: auth validation → call service → return response.
4. Tambahkan input validation dengan Zod di setiap route handler.

**Template Route Handler:**
```typescript
// app/api/helpdesk/tickets/route.ts
import { NextRequest, NextResponse } from 'next/server'
import { getServerSession } from '@/shared/lib/server/auth'
import { getTicketList } from '@/shared/lib/server/services/ticket.server'
import { ticketListSchema } from '@/features/tickets/schemas/ticket.schema'

export async function GET(req: NextRequest) {
  try {
    const session = await getServerSession(req)
    if (!session) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })

    const params = ticketListSchema.parse(Object.fromEntries(req.nextUrl.searchParams))
    const data = await getTicketList(params, session.userId)

    return NextResponse.json(data)
  } catch (error) {
    if (error instanceof ZodError) {
      return NextResponse.json({ error: error.errors }, { status: 400 })
    }
    return NextResponse.json({ error: 'Internal Server Error' }, { status: 500 })
  }
}
```

### STEP 9 — Update `app/(dashboard)/` Layouts dan Pages Menggunakan Server Components

**Estimasi:** 2 jam  
**Risiko:** Sedang

**Konteks:** Dengan fondasi yang sudah bersih, kita bisa memanfaatkan Next.js App Router secara maksimal. Pages seharusnya Server Components yang mem-fetch data awal dan pass ke Client Components.

**Tindakan:**
1. Refactor `app/(dashboard)/page.tsx` (dashboard) menjadi Server Component:
   ```tsx
   // app/(dashboard)/page.tsx — Server Component
   import { getServerSession } from '@/shared/lib/server/auth'
   import { getDashboardStats } from '@/shared/lib/server/services/dashboard.server'
   import { DashboardView } from '@/features/dashboard/components/DashboardView'
   
   export default async function DashboardPage() {
     const session = await getServerSession()
     const stats = await getDashboardStats(session.userId)
     
     return <DashboardView initialStats={stats} />
   }
   ```
2. Tambahkan `loading.tsx` dan `error.tsx` di setiap route segment.
3. Update `app/(dashboard)/layout.tsx` untuk include `RealtimeProvider` sebagai Client Component boundary.
4. Pastikan `middleware.ts` (atau buat jika belum ada) melindungi route `(dashboard)`.

**Buat `src/middleware.ts`** (jika belum ada):
```typescript
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

export function middleware(request: NextRequest) {
  const token = request.cookies.get('access_token')?.value
    || request.headers.get('Authorization')?.replace('Bearer ', '')
  
  const isAuthRoute = request.nextUrl.pathname.startsWith('/login')
  const isDashboardRoute = request.nextUrl.pathname.startsWith('/dashboard')
    || request.nextUrl.pathname.startsWith('/tickets')
    || request.nextUrl.pathname.startsWith('/admin')
  
  if (isDashboardRoute && !token) {
    return NextResponse.redirect(new URL('/login', request.url))
  }
  
  if (isAuthRoute && token) {
    return NextResponse.redirect(new URL('/dashboard', request.url))
  }
  
  return NextResponse.next()
}

export const config = {
  matcher: ['/((?!api|_next/static|_next/image|favicon.ico).*)'],
}
```

## 6. ATURAN ARSITEKTUR (ARCHITECTURE RULES)

Simpan sebagai komentar di `src/README.md` atau enforce via ESLint:

```
✅ DO:
  - Import dari @shared/* di dalam features/
  - Import dari @entities/* di dalam features/
  - Import dari @features/[feature]/* HANYA dari app/ pages
  - Setiap feature memiliki public index.ts

❌ DON'T:
  - import dari @features/tickets/* di dalam @features/auth/* (cross-feature)
  - Taruh business logic di komponen
  - Taruh Prisma calls di Client Components atau hooks
  - Gunakan 'use client' tanpa alasan yang jelas
  - Import server libraries (prisma, jsonwebtoken) di client files
```
